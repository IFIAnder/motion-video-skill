# 电影级收尾：让成片"不像网页录屏"

同样的动效代码，出来的片子可以是"演示录屏"，也可以是"作品集"。差别几乎全在这一层。
下面每一条都来自一个真实作品集级产物（60s / 60fps / 角色骨骼 / 音频同步）的实现方式，
按性价比排序。

---

## 1. 运动模糊：这一条最影响"顺不顺"

**原理**：真实摄影机一帧的曝光不是瞬间的。180° 快门下，曝光时间 = 半帧时长。
这半帧里物体在移动，所以每帧都带着运动方向的拖影。人眼把拖影读成"流畅"；
没有拖影时，24/30fps 的离散帧会让眼睛读成"跳"。

**这就是"同样的动效，为什么别人的看起来很顺"的一半原因。不是更会画，是有快门。**

本 skill 已内置：

```bash
node scripts/render.mjs --html scene.html --out out/v.mp4 --fps 30 --motion-blur 180
# 内部：以 120fps 渲染 360 帧，每 4 帧取 2 帧做时间平均 → 曝光 1/60s = 180° 快门
```

代价：渲染时间 ×4。**迭代阶段可以临时关着省时间，但交付版必须开**——省快门就是在降质。
真要省时间，去杀浪费（并发改串行、批量抽帧、不落盘直通），不要关快门。
**60fps 同理**：有角色动作、甩镜、粒子就上 60，不要因为"渲染翻倍"而退到 30——
30fps 下快速肢体会顿，那是缺陷不是取舍。

什么时候值得开：

| 场景 | 开不开 |
| --- | --- |
| 位移、缩放、旋转、甩镜、粒子 | **开**（收益最大） |
| 纯淡入淡出、文字打字机、静态构图 | 不必（没有相对运动，糊了反而浑） |
| 定格、逐帧抖动（glitch） | 不要（本来就该锐） |
| 60fps 成片 | 180° 即可；360° 会太糊 |

**分部控制**（进阶）：一个片子里有的镜头需要、有的不需要。拆成两个场景文件
分别渲染，再拼。不要一个开关管全片。

## 2. 编码参数：暗部色带的元凶与解药

默认参数出来的片子在暗背景渐变上会有明显色带。工业参数长这样：

```bash
# 画面
-vf "scale=out_color_matrix=bt709:out_range=tv,format=yuv420p,noise=c0s=5:c0f=t+u"
-c:v libx264 -preset slow -crf 14 -tune film -profile:v high -g 120
-color_primaries bt709 -color_trc bt709 -colorspace bt709
-movflags +faststart
# 音频
-c:a aac -b:a 320k
```

关键三点，缺一不可：

1. **`noise=c0s=5:c0f=t+u`** —— 加极轻的时域噪点。这不是"脏"，这是**抖动（dither）**，
   用来打散 8bit 量化在暗部渐变上的台阶。crf 越低越需要它。
2. **显式标记 bt709** —— 不标记时播放器按各自猜的色彩空间解，你的紫会变成别人的蓝。
3. **`-tune film` + `-g 120`** —— `film` 保留颗粒感，`-g 120` 让关键帧稀疏（画质更稳、体积更小）。

`crf 14` 是作品集档位；`17` 是通用档；`20+` 是预览档。**别用 crf 23 交付。**

## 3. 暗角（vignette）：两行代码的"聚焦"

```js
const v = g.createRadialGradient(960, 540, 500, 960, 540, 1150);
v.addColorStop(0, 'rgba(0,0,0,0)');
v.addColorStop(1, 'rgba(0,0,0,.42)');
g.fillStyle = v; g.fillRect(0, 0, W, H);
```

作用：把视线压向中心、压掉边角的杂色、让整体"暗得统一"。
有亮色段落时换成带色调的暗角（`rgba(60,20,110,.16)`），否则边缘会显脏。

## 4. HUD 系统：作品集感的载体

一个作品集短片和"几个动效拼在一起"的区别，往往是**有没有贯穿全片的信息层**。
可用元素（都是 Canvas 几行代码）：

| 元素 | 代码要点 | 为什么有用 |
| --- | --- | --- |
| 四角裁切标记 | 四条 L 形折线，`m=40, L=26` | 立刻"取景器/监视器"感 |
| 时间码 | `TC 00:MM:SS:FF` 按帧号算 | 让人觉得"这是成片不是预览" |
| 帧号 / 总帧 | `F 0130/3600` | 同上，且便于对帧调试 |
| 格式标注 | `1920×1080 · 60FPS · 180° SHUTTER` | 展示"我知道自己在做什么" |
| 进度条 | 底部细线 `t/DUR` | 长片的呼吸感 |
| 章节号滚动 | 裁剪 + `translateY` 入场 | 章节切换的连续感 |
| REC 闪烁 | `Math.floor(t*2)%2===0` | 极便宜的生命感 |
| 胶片齿孔 | 上下两排等距小方块 | 只在"胶片"主题段落用 |

**纪律**：HUD 全程 `globalAlpha` 弱化（0.75 左右），且要在亮色段落自动换成深色。
它应该是氛围，不是主角。台词/主体内容永远压过 HUD。

```js
const isLight = (t) => t >= LIGHT_FROM && t < LIGHT_TO;
const col = isLight(t) ? 'rgba(18,13,28,.75)' : 'rgba(228,219,255,.8)';
```

## 5. 甩镜转场（whip pan）：两个场景同框

比"淡出淡入"高级一个档，实现极简单：两个场景同时画，各自被推出/推入。

```js
const [w0, w1] = [31.7, 32.0];
const u = easeInOutExpo(seg(t, w0, w1));
g.save(); g.translate(-u * 1920, 0); scenePrev(g, t); g.restore();   // 左边被推出
g.save(); g.translate((1 - u) * 1920, 0); sceneNext(g, t); g.restore(); // 右边进来
```

配上运动模糊（`--motion-blur 180`）就是标准甩镜。**注意**：两个场景都要能在
同一时刻被渲染（`scenePrev`/`sceneNext` 只读 `t`，不持有状态——纯函数的好处）。

## 6. 帧率：30 还是 60

| 内容 | 帧率 | 理由 |
| --- | --- | --- |
| 片头/UI/图表/文字动效 | 30 | 够了，省一半渲染与体积 |
| 角色动作、快速位移、甩镜、粒子 | **60** | 30fps 下快速肢体动会顿 |
| 循环动图 gif | 15–20 | 体积优先 |

60fps 的真实成本：渲染 ×2、编码 ×1.6、体积 ×1.7。**只在真有快速运动时值得。**
另外 60fps 时快门角度换算不变（180° 仍是半帧），但曝光时间减半，模糊感更细。

## 7. 长片怎么组织（> 20 秒）

不要把所有时间点散落在场景代码里，会失控。用一个**常量表**当唯一事实源：

```js
// cues.js —— 视觉和音频共用同一份
const BPM = 120, BAR = 4 * 60 / BPM;    // 2s 一小节
const CHAPTERS = [
  [0.0,  '01', 'FOUNDATION', '基础'],
  [11.85,'02', 'RIG',        '骨骼'],
  [22.0, '03', 'ANIMATE',    '角色动画'],
];
const ACT = {
  t0: 22.0, squat: 22.85, takeoff: 23.1, land: 23.65, height: 140,
  wave: [23.95, 24.95],
};
ACT.apex = (ACT.takeoff + ACT.land) / 2;   // 派生量也算在这里
```

**派生量必须算，不许手填**：落地时间、顶点时刻、错开序列、雷达扫描反解——
全部由公式或二分算出。手填的 0.1 秒偏差会在成片里变成"卡了一下"。

场景函数只做一件事：`if (t < cues.B.zoom[1]) return sceneA(g, t)`。
时间表改了，全片跟着改。

## 8. 音频同步（有配乐时）

三步，别跳：

1. **定网格**：BPM → 一小节时长。120BPM = 2s/小节 = 每 0.5s 一个拍点。
   所有转场、字形落地、角色起跳都吸附到这个网格上。
2. **分析**：`ffmpeg -i music.flac -af "aresample=8000,astats" -f null -` 或用脚本
   做能量包络（RMS），拿到每 0.1s 的能量序列，找峰值作为强调点。
   （真实项目会生成一份 `analysis.json`，十几万行都不奇怪。）
3. **对齐**：把分析出的峰值写回 `cues.js`，让画面事件落在峰上。
   合成时 `-ss <起始时间> -i audio.wav -map 0:v -map 1:a -shortest`。

没有配乐时，仍然建议按 **BPM 网格**排节奏——人的节奏感来自拍点。

## 9. 提速：长片才需要的两招

小片（< 15s）用 `render.mjs` 单页渲染够用。上百秒的片子要做两件事：

**① 多页并行**：**已内置，`--jobs N`，默认按核数自动取（上限 4）。**

一个 Chrome 里开 N 个 target，共享游标领帧（谁渲完谁领下一帧，比静态分段更能自动均衡）。
实测（1920×1080 @30fps，同一台 32 核机器，含启动与编码开销）：

| 场景 | `--jobs 1` | `--jobs 4` | `--jobs 8` | `--jobs 16` |
| --- | --- | --- | --- | --- |
| `examples/demo-scene.html` 240 帧 | 24.9s | **15.6s** | 15.5s | — |
| `examples/illustrated-scene.html` 180 帧 | 24.8s | **15.7s** | 23.2s | 15.6s |

**加速比 1.57–1.60 倍，4 路就饱和了。** 8 路、16 路都没有额外收益，甚至回退——
瓶颈不在核数，而在**浏览器进程把截图序列化**这一步（多 tab 只能并行光栅化，不能并行 PNG 编码与读回）。

**像素代价**：跨 tab 渲染同一帧，与单 tab 的差异是 LSB 级——
实测 PSNR 53.8 / 55.3 / 111.3 dB，SSIM 0.99984–1.000000。人眼看不出，编码后基本消失。
所以交付版可以放心用 `--jobs 4`；但**要逐字节复现上一次的输出**（回归测试、像素级 diff），
请用 `--jobs 1 --gl swift`，两次渲染才可比。

**② 不落盘**（还没实现）：页面暴露 `window.frameURL(t)` 返回 PNG dataURL，
直接 `Buffer.from(base64)` 塞进 `ffmpeg -f image2pipe -framerate 60 -i -`。
省掉几千次磁盘写。`render.mjs` 目前走落盘 PNG 路线（简单、可断点、`--keep-frames` 可复盘），
短片够用；一帧约 1.5 MB，240 帧就是 360 MB 的写入加再读取，长片上是实打实的一二十个百分点。

### ③ GPU 渲染：分场景，别一概而论

`render.mjs --gl` 控制 Chrome 的图形后端。默认 `auto`（有显卡就走 GPU），`--gl swift` 强制软件渲染。

实测（1920x1080，60 帧，同一台机器）：

| 场景 | `--gl swift` | `--gl auto` | 结论 |
| --- | --- | --- | --- |
| 24 层 `filter: blur()` + `mix-blend-mode` | **26.4s** | **15.4s** | GPU 快 1.7 倍 |
| 普通 DOM（`examples/demo-scene.html`） | 15.4s | 15.4s | 一样快 |

**为什么普通场景没差别**：90 帧的总时间里 13.5s 花在逐帧 CDP 截图（合成 → 读回 → PNG 编码），
只有 2.1s 是 ffmpeg 编码。这三步全在 CPU 上，GPU 帮不上忙。
而 `filter` / `blur` / `backdrop-filter` / `mix-blend-mode` 每帧都要重新光栅化 —— 那里才是 GPU 的主场。

**代价**：两种后端像素不完全相同（同一场景 md5 就差几个字节，抗锯齿与混合的细微差别）。
`audit` 的判定不受影响（实测 PASS/PASS，变化峰值差 0.03%），但**需要"重渲染后逐像素一致"时用 `--gl swift`**：

- 迭代阶段 → 默认 `auto`，快
- 要对比"改完之后画面有没有意外变化" → `--gl swift`，两次渲染才可比
- 交付版 → 两种都行；但如果你的机器没有独立显卡，`auto` 会自动回落到 `swift`，不会失败

## 10. 交付前最后一遍

```bash
node scripts/render.mjs --html scene.html --out out/final.mp4 --fps 30 --motion-blur 180
node scripts/audit.mjs --video out/final.mp4 --fps 30 --duration 3 --width 1920 --height 1080
ffprobe -v error -show_entries stream=codec_name,r_frame_rate,nb_frames -of default=nw=1 out/final.mp4
```

- 运动段有没有拖影？关掉模糊再看一次，确认差异是"更顺"而不是"更糊"
- 暗部有没有色带？有 → `noise=c0s=5` 加上了吗
- 亮色段落 HUD 换色了吗
- 时间码/帧号算对了吗（末帧 = 总帧数 - 1）
