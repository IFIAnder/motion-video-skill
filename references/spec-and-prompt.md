# 规格模板 与 可直接复制的 prompt

两种用法：
- 加载了本 skill 时，这里的表格是 STEP 1 的产出格式；
- 没加载 skill、只想在别的会话/别的模型上补差距时，直接复制 §2 的 prompt。

---

## 1. storyboard 模板

复制成 `storyboard.md` 填。填不满就别写代码。

```markdown
# <项目名>

- 用途：<片头 / 社交竖屏 / 网页 hero / 数据动效 / 讲解插片>
- 尺寸：1920x1080   帧率：30   时长：3.0s   循环：否
- 情绪：稳 / 快 / 柔 / 硬
- 三色 + 一强调色：#0b0e14 底 / #eaf1ff 主文字 / #6d8bbd 次文字 / #6ee7ff 强调

## 镜头表
| # | 时间 | 画面在做什么 | 主要运动 | 收尾状态 |
|---|------|--------------|----------|----------|
| 1 | 0.00–1.10 | 标题逐字上浮 | y +96→0，字间错开 75ms | 标题就位 |

## 元素时间轴
| 元素 | enter | active | exit | 属性 | 曲线 |
|------|-------|--------|------|------|------|
| #title span | 0.15+i*0.075 | →片尾 | — | translateY 96→0 / opacity 0→1 | easeOutCubic |
| #bar b | 0.30 | 0.30–2.40 | — | scaleX 0→1 | easeInOutCubic |
| .dots i | 1.50+i*0.15 | →片尾 | — | scale 0→1 | easeOutBack |

## 节奏图（每 0.5s 一格，密度表示运动量）
0.0 ▁▂▄▆ 1.0 ▆▄▂▁ 2.0 ▂▁▁▁ 3.0
（前段密集 = 入场，中段低 = 停留，后段小峰 = 收尾）

## 验收标准（交付时必须逐条满足）
- [ ] audit verdict = PASS 或每条 WARN 有解释
- [ ] 无中段静止（除非节奏图里标了停留）
- [ ] 文字不溢出安全区（四边 80px）
- [ ] 暗背景上次文字对比度 ≥ 4.5:1
```

## 2. 三种启动 prompt（复制即用）

### A · 规格先行（最通用，默认用这个）

> 请按下面的顺序做，不要跳过任何一步：
>
> **第一步：先只输出规格，不写代码。**
> 产出一张元素时间轴表，列：元素 / enter(秒) / active(秒区间) / exit(秒区间) / 变化的属性 / 缓动函数。
> 每个元素必须有 enter、active、exit 三项；如果某元素从头活到尾，exit 写「—」并说明到片尾。
> 时长 <duration>、尺寸 <WxH>、帧率 30。
>
> **第二步：我确认表之后，再写实现。**
> 实现必须满足：一个 `window.scene = { duration, fps, width, height, ready, seek(t) }`，
> 所有画面状态是 `t` 的纯函数 —— 禁止 requestAnimationFrame、Date.now、performance.now、
> Math.random、自增计数器、以及会自己跑的 CSS @keyframes。
> 所有 CSS/JS 内联，字体用系统字体，不引外部 CDN。
>
> **第三步：自查。**
> 逐条回答：每个元素在 active 区间内是否每帧都在变化？有没有哪个元素只有入场函数？
> 0 到 duration 之间是否存在任何 "画面完全不动" 的 0.5 秒以上区间？
> 末帧（t = duration - 1/30）是否停在设计要的收尾状态？

为什么这样写有效：第一步把审美降维成表格，第三步强迫它自查"中间态"。
直接说"做个好看的动画"时，模型给你的通常是"写了两端、中间靠 CSS 过渡"。

### B · 自验回环（有 render/audit 脚本时）

> 写完后按这个循环处理，最多 5 轮：
> 1. `node scripts/render.mjs --html scene.html --out out/v.mp4 --fps 30 --sheet`
> 2. `node scripts/audit.mjs --video out/v.mp4 --fps 30 --duration <d> --width <W> --height <H>`
> 3. audit 的每条 FAIL/WARN：要么改代码，要么明确写出「这是设计内的，因为 …」。不许静默忽略。
> 4. 若是 FAIL，回到第 1 步；直到 verdict 变成 PASS 或只剩你已解释过的 WARN。
>
> 改的时候一次只改被点名的那一处，改完立刻重跑——不要一次改五处然后重新开始。

### C · 复刻参考（想拉平审美差距时最有效）

> 参考：【附一张图 / 一帧截图 / 一段片的截图序列】。
> 不要原创构图，按参考复刻：
> 1. 先描述参考的**版面结构**：分几个区域、各区域占比、视觉重心在哪、留白多少。
> 2. 再描述它的**层级**：字号比、颜色层级（几个灰阶）、强调色用在哪。
> 3. 然后写规格表（同 prompt A 第一步）。
> 4. 最后实现，并在 audit 之外自己核对：与参考的版面差异是什么。
>
> 复刻时禁止"我觉得更好"的改动；要改就单独列出，等我选。

**这是最被低估的一条。** 小模型原创构图必然平庸，但给它一张图让它复刻，
它能做得相当接近——因为复刻是"受约束的转录"，正是它的强项。

## 3. 反面例子（为什么这些话没用）

| 你说 | 模型听到的 | 结果 |
| --- | --- | --- |
| 「做个好看的动画」 | 无约束创作空间 | 2010 年 PPT 风，居中大字 + 淡入 |
| 「要高级感」 | 一个形容词，没有对应操作 | 加一堆阴影和渐变，更廉价 |
| 「参考 Apple 的风格」 | 模糊的品牌联想 | 抄了黑白配色，没抄排版 |
| 「细节丰富一点」 | 加东西 | 塞满画面，没有留白 |
| 「用 remotion 写」 | 换成 API，约束不变 | 仍然是只有首末帧 |

替换成：**具体数值 + 参考 + 验收标准**。

## 4. 强弱模型的 prompt 差异

同一套 prompt，给不同模型要调比例：

| | 小模型（Flash / mini） | 强模型（Opus 级） |
| --- | --- | --- |
| 规格表 | **强制**，必须逐格填 | 可省，让它自己列 |
| 步骤拆分 | 一步一确认，别一次给全部 | 可一次完成 |
| 参考素材 | **强烈建议**给 | 可选，给了可能压住它 |
| 自查要求 | 必须逐条书面回答 | 一句"自查"就够 |
| 迭代 | 每次只改一处 | 可批量改 |
| 自由度 | 收紧，用表格代替形容词 | 放宽，允许它判断 |

核心原则：**模型越弱，越要把任务从"创作"改成"填空"**。
不是零和——填空填得足够细，产出的天花板也是由规格决定的，不是由模型决定的。

## 5. 对付"能自己算就绝不调工具"的模型

有些模型（Flash 级尤其明显）会省工具调用：它觉得心算更快，于是自己估贝塞尔控制点、
自己估错开步长、自己估对比度。结果是**错误很安静**——曲线不报错，只是不丝滑；
步长不报错，只是所有元素糊在一起。你事后很难指出它错在哪。

它不是在偷懒，是**成本账算错了**。所以别骂它，把账摆出来，再把要求写成可判定的形式。

### 5.1 先给它正确的成本函数

> 你有一个倾向：能自己算就不调脚本。先看这笔账再决定。
>
> 心算一条 cubic-bezier：耗时 0，一次估对的概率约三四成。估错的代价是
> 渲 90 帧（约 8 秒）+ 审图，而且**通常看不出来错**，只表现为"不够丝滑"这种没人能定位的问题。
> 期望成本 ≈ 0 + 0.5 × 38 ≈ **19 秒**，并且质量静默下降。
>
> 调 `node scripts/ease.mjs cubic ...`：耗时 0.5 秒，0 错误率，输出直接能粘。
>
> 所以规则是：**任何曲线参数、弹簧参数、错开步长、坐标换算、对比度比值，
> 都必须来自工具输出，不许在回答里手写推断值。** 这不是风格问题。

### 5.2 把约束写成"可判定"，而不是"要努力"

不要写"尽量用工具"。写成能被检查的形式：

> 在你写出任何缓动参数之前，必须先有一条 `node scripts/ease.mjs ...` 的输出。
> 交付时自检：把回答里出现的每个数字，逐一指向上一条命令的输出。
> 有任何一个数字指不出来，就是违规，删掉重跑。
>
> 你说"这条曲线很丝滑"之前，必须已经看过工具打的 ASCII 图和过冲百分比。

### 5.3 给它留一个"验证"的出口

它想自己验，是因为它不信任自己的记忆。那就把验证动作具体化：

> 你想"再确认一下"的时候，正确动作是跑 `verify.mjs`，不是在心里模拟一遍。
> `verify.mjs` 读的是浏览器里的真实计算样式：
> `node scripts/verify.mjs --html scene.html --select "#bar b" --props transform --steps 31`
> 它会告诉你每个元素每个时刻的精确值、有没有中途停顿、有没有 NaN。
> 它还会用 `--idempotent` 证明"同一 t 两次调用结果一致"——这是"画面只由 t 决定"的机器证明。

### 5.4 顺序本身就是防作弊设计

把工具调用放进**不可跳过的流程节点**，它就没有"要不要用"的选择：

```
ease（算参数）→ 填进规格表 → 写代码 → verify（查数字）→ render（出图）→ audit（查像素）→ 人眼
```

规格表里「曲线」那一列不许只写 `easeOutCubic`，必须写工具确认过的形态
（含过冲百分比和平台段）。这一列填不出来，就说明它跳过了 `ease`。

### 5.5 什么时候可以允许它自己算

说清楚边界，否则它会拿边界当借口：

- 可以自己算：一次加减、一个比例（`0.3 + 0.1 = 0.4`）、把一个已知值抄进代码
- 必须跑工具：所有**曲线形状**、所有**到达/稳定时间**、所有**多个元素的相对节奏**、
  所有**颜色是否可读**、所有**输出给 CSS 的 `linear()` 串**

分界线：**算错了会不会静默影响观感**。会 → 跑工具。不会 → 随便。
