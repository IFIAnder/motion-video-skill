# 许愿式创作：一句话就要出片，不许做访谈

前面几份文档都建立在"有规格表"之上。但真实的使用场景往往是一句话：

> 制作一段动态的 15 秒动效视频，展示你是一位多么出色的动效设计师。
> 标题是「★Ander.」，人物素材已经在工作空间中。就像作品集短片那样，全力以赴。

这种输入**没有**尺寸、没有章节、没有曲线、没有配色。它的产出上限却可以很高。
本文讲清为什么，以及怎么让弱模型也能接住。

## 一、先分清两种输入

| | 下需求 | 许愿 |
| --- | --- | --- |
| 典型说法 | 「3 秒 1080p 片头，标题"星野"，紫金色，要高级」 | 「做个厉害的东西，展示你的能力」 |
| 约束在哪 | 在话里 | **不在话里，要靠你补** |
| 你该做的 | 照做 + 验收 | **先补全，再照做，最后说明补了什么** |
| 致命错误 | 擅自改需求 | **反问用户做访谈**（许愿者最讨厌这个） |

许愿不是"需求写得差"，它是一种授权：**"我不管你怎么做，我要结果"**。
对它做访谈，等于把创作责任推回去，体验立刻崩。

## 二、一段话为什么能出大作：四个槽位

把那段 prompt 拆开看，它其实给了四样东西，缺一项结果就完全不同：

| 槽位 | 那句话里的对应 | 缺了会怎样 |
| --- | --- | --- |
| **母题**（围绕什么组织） | 「人物素材已经在工作空间中」 | 变成抽象图形堆砌，没有主角，看完记不住 |
| **元叙事**（为什么而做） | 「展示你是一位多么出色的动效设计师」 | 变成一个孤立的动效，做完就完了 |
| **形式**（长成什么样） | 「就像作品集短片那样」 | 变成"一个大动效"，而不是"有章节的片子" |
| **档位**（做到什么程度） | 「全力以赴」 | 保守、只做安全的东西、处处收着 |

**元叙事是最高杠杆的一项。**"展示你的能力"会自动导出一条推导链：

```
证明我很会动效
  → 动效由什么构成？缓动曲线、字体运动、角色动作、节奏、风格、循环
  → 每一项都给一个可演示的单元
  → 串成章节 → 需要贯穿的框架（HUD）把它们缝起来
```

这一句话就替代了整份 storyboard。**这是短 prompt 能赢的真正原因：它把"选题"解决了。**

## 三、许愿模式流程（不许问）

### STEP W0 · 先扫工作空间，不是先设计

**这是最容易被跳过、但决定成品好坏的唯一步骤。**

```bash
# 找素材、字体、既有代码、音频
ls / tree 工作目录（排除 node_modules）
```

要找四类东西，找到什么就围绕什么做：

| 找到 | 它变成什么 |
| --- | --- |
| 角色/产品图/logo 切图 | **母题**：全片的视觉锚，反复出现 |
| 字体文件（ttf/woff2） | 排版性格。有 condensed 就别用系统默认 |
| 音频（音乐/音效） | **节拍网格**：所有转场吸附到拍点，观感立刻上一个档 |
| 既有代码/组件 | 复用，别重写 |

那句 prompt 里最关键的不是"展示能力"，是**"人物素材已经在工作空间中"**——
它把创作从"凭空想象"变成"围绕既有素材组织"。凭空想象是弱模型最弱的地方，
围绕素材组织是它最擅长的地方。

**工作空间里什么素材都没有时**，才允许进入"纯程序化图形"路线（用
[asset-recipes.md](asset-recipes.md) 的 20 类片段把画面填满），并且仍然不许反问。

### STEP W1 · 自己把四个槽位填满

不许问，用默认值填。填完写进 `storyboard.md` 开头四行，作为后面一切的依据。

**默认值表**（许愿模式下直接采用，不问）：

| 项目 | 默认 | 例外 |
| --- | --- | --- |
| 尺寸 | 1920×1080 | 说"竖屏/抖音/小红书"→1080×1920；说"方形"→1080×1080 |
| 时长 | 见下"章节预算" | 说了时长就照办 |
| 帧率 | 有角色动/甩镜 → 60；纯 UI/文字 → 30 | — |
| 格式 | mp4（H.264） | 说"动图"→gif；说"网页用"→webm |
| 情绪 | 由素材定：角色活泼→明快；产品图→克制 | — |
| 配色 | 3 色 + 1 强调，从素材取主色 | 说了品牌色就用 |
| 结构 | 元叙事推导（见下） | 说了"分几段"就按它 |

### STEP W2 · 元叙事 → 章节（这是许愿模式的核心算法）

如果用户说的是"展示你的 X 能力"，就按这个模板展开。以动效为例：

```
01 基础       ——  缓动曲线（画 3 条曲线，小球沿曲线跑）
02 字体       ——  动态字（逐字入场 / 字重变化 / 字距呼吸）
03 素材       ——  把母题拆开给你看（部件分解 → 组合，或产品多视角）
04 主体动作   ——  母题做一件有性格的事（跳、挥、转、变形）
05 原理       ——  用字幕列出"我懂什么"，让母题逐条演示
06 变体       ——  同一内容的 N 种风格（换色/换质感/换运动语言）
07 循环       ——  2 个可无限循环的小动效（证明能做 loop）
08 收尾       ——  标题卡 + 招呼（把品牌/名字落地）
```

**每一章必须能在 2–5 秒内说清一件事。** 说不清就拆，别合并。

如果用户说的是别的能力（比如"展示我们的产品"，不是"展示你"），把章节换成：

```
问题 → 产品如何解决 → 关键机制拆解 → 数据/规模 → 场景 → 收尾
```

通用规律：**元叙事 = "证明式结构"**，先给能力，再给证据，最后落到一个具体的落脚点。

### STEP W3 · 章节预算：宁少勿滥

许愿模式最常见的失败是**大杂烩**：每样都做一点，都不深。

| 总时长 | 章节数 | 每章时长 | 帧数@60fps |
| --- | --- | --- | --- |
| 10–15s | 3–4 章 | 3–4s | 180–240 |
| 20–30s | 5–6 章 | 4–6s | 240–360 |
| 45–60s | 7–9 章 | 5–8s | 300–480 |

**每章一个主角效果，别叠。** 一章里既有扫光、又有粒子、又有 3D 翻转 = 没有重点。

每章开工前先写下这一章的"一句话目标"和"可演示点"：

```
04 ANIMATE —— 目标：证明角色是有重量的；可演示点：起跳的预备/滞空/落地挤压
```

写不出来 = 这章不该存在，删掉或合并。

### STEP W4 · 把"确认"从用户身上转到机器身上

许愿模式的纪律全在这里。你不问用户，就必须自己当那个挑刺的人，
而且要用**机器判定**而不是自我感觉：

```
每章：写 → verify（数值）→ render --still 3 帧（构图）→ audit（运动）→ 改
全片：拼 → audit（黑帧/时长）→ 定稿开 --motion-blur → audit
```

三层分工要记牢：

- `verify` 说"这个元素这一段的数值没变" → 中间态丢了
- `audit` 说"1.1–2.5s 整帧静止" → 观众会看到停滞
- `--still` + 肉眼说"标题压过安全区了" → 构图问题（`--guides` 辅助）

**许愿模式下，允许交付"有 WARN 但有解释"的版本，不允许交付"没跑过 audit"的版本。**

### STEP W5 · 交付时说明你替他做了哪些决定

许愿者授权你决定，但他有权知道你决定了什么。交付说明固定三段：

1. **我补了哪些槽位**：母题取的是哪个素材、元叙事选的是哪种、结构怎么排的
2. **我替你定了哪些默认值**：尺寸/帧率/时长/配色，以及为什么
3. **已知妥协**：哪一章最弱、哪里是赶出来的、哪里还能再加

第 3 段最容易被省略，也最建立信任。**主动说短板，比等对方发现强。**

## 四、许愿模式的三种失败形态

| 症状 | 原因 | 修 |
| --- | --- | --- |
| **大杂烩**：每章都塞 3 个效果，看完记不住任何一个 | 没有章节预算 | 一章一个主角效果，其余全删 |
| **保守**：全片只有淡入淡出 + 平移，不敢画 | 怕画错（见 [asset-recipes.md](asset-recipes.md)） | 每章至少 2 个自建视觉元素 |
| **只在头尾用力**：第 1 章和第 8 章很漂亮，中间 6 章像 PPT | 精力分配错了 | 先给每章定"可演示点"，再动手；中段章节优先做 |

还有一个隐蔽的：**中段停滞**。许愿模式下模型容易把长章节做成"入场 + 长时间静止 + 出场"。
`audit` 的中段静止检测专抓这个，别忽略它的 WARN。

## 五、唯一该回头问的情况

只有一种：**工作空间里既没有素材、也没有任何能当母题的东西，而用户又要求"围绕某个具体对象"**。
这时问一句就够："母题用什么？给我一张图、一个 logo 或一个名字。"

其他一切（尺寸、时长、颜色、结构、风格、帧率）都不许问，自己定。

## 六、可直接复制的许愿模板

如果想让弱模型复刻"一句话出片"，把这四个槽位写全（比原 prompt 只长了一点）：

```
做一段 <时长> 的 <形式>，主题是「<标题>」。
目标：展示 <你要证明的能力>。
素材：<工作空间里有什么，或"自己用代码画">。
参照：<像什么>（作品集短片 / 发布会片头 / 产品宣传 / 音乐可视化）。
质量：全力以赴，不要保守。
```

对照那份成功的 prompt，只有"素材"被明确化了——**这一项最值得补**，
因为它是弱模型唯一需要被指路的地方（它不会自己去找素材）。

## 七、和强约束路线的取舍

| | 许愿模式 | 规格模式 |
| --- | --- | --- |
| 适合 | 强模型；有素材；展示型内容；时间宽裕 | 弱模型；无素材；有明确交付物；要可复现 |
| 弱点 | 结果不可预测，差一点就变成杂烩 | 需要来回确认，创作自由度低 |
| 共同点 | **两层都必须跑回环**。区别只在"规格是自己填的还是用户给的" |

结论：**许愿是输入方式，不是质量豁免。** 一句话进来，可以一句话不问就开工，
但规格表还是要有——只是那张表现在是你写的，写在 `storyboard.md` 里，
不是问用户要来的。
